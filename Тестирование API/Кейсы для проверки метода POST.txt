Негативные кейсы (безопасность и целостность):

SQL-инъекции в текстовых полях (email, имя, адрес) — например, ' OR 1=1 --.

XSS-инъекции в имени пользователя и адресе — например, <script>alert(1)</script>.

Дублирование email — регистрация с уже существующим в базе email.

Дублирование телефона — регистрация с уже существующим номером.

Дублирование имени пользователя — если имя пользователя уникально.

Регистр в email — проверка, что Test@Mail.com и test@mail.com не создают двух разных пользователей (или создают — в зависимости от требований).

Пробелы в начале/конце значений полей (email, имя, телефон) — должны либо тримиться, либо отклоняться.

Превышение максимальной длины полей (email, имя, адрес, телефон).

Невалидный формат email — без @, без домена, с пробелами, с двумя @.

Невалидный формат телефона — буквы, слишком короткий/длинный номер, неверный код страны.

Невалидные символы в имени пользователя — спецсимволы, эмодзи, пробелы (если запрещены).

Некорректный JSON в теле запроса — битый синтаксис, лишние поля, отсутствие Content-Type: application/json.

Пустое тело запроса — {} или полностью пустое.

Передача null в обязательных полях.

Передача неверных типов — например, число вместо строки в email, объект вместо строки в имени.

Очень большое тело запроса — проверка лимита размера (например, адрес на 10 МБ).

Отсутствие Content-Type или неверный Content-Type (например, text/plain).

Отправка запроса на неверный endpoint — например, POST /api/users/register/ вместо /api/register/.

Повторная отправка того же запроса (идемпотентность) — должен ли создаваться дубль или возвращаться ошибка.

CSRF-защита — если регистрация идёт через браузер, проверка наличия/отсутствия CSRF-токена.

Rate limiting — слишком много запросов на регистрацию с одного IP за короткое время.

Регистрация с email, содержащим Unicode-символы (например, кириллицу) — если требуется только ASCII.

Регистрация с телефоном в формате, не поддерживаемом системой (например, без кода страны).

Позитивные кейсы (расширение):

Регистрация с минимальной длиной допустимых значений (например, имя из 1 символа, если разрешено).

Регистрация с максимальной длиной допустимых значений (граничные значения).

Регистрация с email в верхнем регистре — должен ли он нормализоваться.

Регистрация с телефоном в разных форматах — +7 999 123-45-67, 89991234567, +79991234567 — если система поддерживает нормализацию.

Регистрация с адресом, содержащим спецсимволы (например, ул. Ленина, д. 1/2, кв. 3).

Регистрация с именем, содержащим дефис/апостроф (например, Анна-Мария, O'Brien).

Регистрация с email на поддомене (user@mail.co.uk).

Регистрация с интернационализированным email (IDN, если поддерживается).

Регистрация с телефоном, содержащим добавочный номер (если поддерживается).

Регистрация с адресом в нестандартном формате (если поле свободное).

Проверки ответа и побочных эффектов:

Код ответа — 201 Created (или 200 OK), а не 500/400 при валидных данных.

Тело ответа — содержит ли ожидаемые поля (id пользователя, сообщение), нет ли утечки чувствительных данных (пароль, хеш).

Заголовки ответа — Content-Type: application/json, отсутствие лишних заголовков.

Фактическое сохранение в БД — пользователь действительно появился в базе с корректными данными.

Хеширование пароля (если есть пароль) — в БД не хранится открытый пароль.

Отправка приветственного письма/SMS — если предусмотрено, проверка факта отправки.

Логирование — событие регистрации залогировано без чувствительных данных.

Транзакционность — если регистрация включает несколько шагов (создание пользователя + профиля), при ошибке на любом шаге не должно оставаться «полу-созданных» записей.

Уникальность ID — сгенерированный ID не повторяется при параллельных запросах.

Параллельная регистрация — два одновременных запроса с одним и тем же email: один должен успешно создать пользователя, второй — вернуть ошибку дублирования (race condition).

Проверки методов и заголовков (расширение ваших кейсов):

GET, PUT, PATCH, DELETE, OPTIONS, HEAD на endpoint регистрации — должны возвращать 405 Method Not Allowed (кроме OPTIONS, если CORS).

Отсутствие заголовка Authorization — если регистрация не требует авторизации, запрос должен проходить; если требует — 401.

Неверный Authorization — если endpoint защищён.

Отсутствие Accept — должен ли сервер вернуть JSON по умолчанию.

Accept: application/xml — если сервер поддерживает только JSON, должен вернуть 406 Not Acceptable или JSON.

Отсутствие User-Agent — должен ли запрос проходить.

Проверки граничных и особых случаев:

Регистрация с email, который уже был удалён (soft delete) — можно ли зарегистрироваться повторно.

Регистрация с телефоном, который уже был удалён — аналогично.

Регистрация с email, содержащим + (например, user+test@mail.com) — должен ли считаться уникальным.

Регистрация с email, содержащим точку в локальной части (user.name@mail.com) — нормализация.

Регистрация с адресом, содержащим только пробелы — если поле необязательное, должно ли оно считаться пустым.

Регистрация с именем, состоящим только из пробелов — должно ли отклоняться.

Регистрация с телефоном, содержащим только пробелы/спецсимволы — должно ли отклоняться.

Регистрация с email, содержащим только пробелы — должно ли отклоняться.

Регистрация с очень длинным email (например, 320 символов — граница по RFC).

Регистрация с email, содержащим два @ — должно ли отклоняться.

Регистрация с email, содержащим точки в домене (user@mail..com) — должно ли отклоняться.

Регистрация с телефоном, содержащим буквы — должно ли отклоняться.

Регистрация с телефоном, содержащим только + — должно ли отклоняться.

Проверки безопасности (дополнительно):

Mass assignment — передача лишних полей, например "is_admin": true, "role": "admin" — сервер не должен их принимать.

Подмена типа — передача "email": ["a@b.com"] вместо строки.

Prototype pollution — передача "__proto__": {"isAdmin": true} (для JS-бэкендов).

NoSQL-инъекции — если используется MongoDB, передача {"$ne": null} в полях.

HTTP-параметр pollution — если параметры дублируются в query string.

Проверка на утечку информации — сообщение об ошибке не должно раскрывать, существует ли email/телефон (если это требование безопасности).

Проверка на timing attack — время ответа при существующем и несуществующем email не должно различаться (если это критично).

Проверки производительности и нагрузки:

Регистрация при высокой нагрузке — 100 одновременных запросов с разными данными.

Регистрация при высокой нагрузке с одинаковым email — race condition.

Время ответа — укладывается ли в SLA (например, < 500 мс).

Размер ответа — не слишком ли большой.

Память/CPU — не происходит ли утечек при массовых запросах.

Проверки совместимости и окружения:

Разные клиенты — браузер, мобильное приложение, Postman, curl.

Разные кодировки — UTF-8, UTF-16 в теле запроса.

Разные версии API — если есть версионирование, проверка на /v1/register и /v2/register.

Работа за прокси/балансировщиком — корректно ли определяется IP клиента для rate limiting.

Работа с включённым/выключенным HTTPS — должен ли endpoint требовать HTTPS.

Проверки документации и контракта:

Соответствие OpenAPI/Swagger — все поля, типы, обязательность, коды ответов совпадают с документацией.

Соответствие примерам из документации — запрос из примера должен работать.

Обратная совместимость — если добавляется новое обязательное поле, старые клиенты не должны ломаться (или должны получать понятную ошибку).
